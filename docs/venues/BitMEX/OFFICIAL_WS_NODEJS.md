# bitmex-realtime-api (nodejs) — Full Summary

A reference WebSocket client library for the BitMEX real-time API.
Source: `../../../api-connectors/official-ws/nodejs/`

---

## What it does

Connects to BitMEX WebSocket, maintains an in-memory snapshot of the order book / market state per table and symbol, and exposes it via an EventEmitter interface. It accumulates deltas (partial → insert/update/delete) so callers always have the full current state without needing to manage it themselves.

---

## Protocol: how BitMEX WebSocket works

This is the most useful section — understanding the protocol is the foundation for building a local WS clone.

### Connection

```
wss://ws.bitmex.com/realtime          (production)
wss://ws.testnet.bitmex.com/realtime  (testnet)
```

Authentication (if needed): API key + HMAC-signed nonce appended as query string parameters. Public streams don't require auth.

### Subscribe / Unsubscribe

Client sends JSON:
```json
{ "op": "subscribe", "args": ["trade:XBTUSD", "orderBookL2:XBTUSD"] }
{ "op": "unsubscribe", "args": ["trade:XBTUSD"] }
```

`args` can be `["tableName:SYMBOL"]` or just `["tableName"]` for no-symbol tables.
The nodejs client sends all channels in a single subscribe message after `open`.

### Server responses

**Info message** (sent on connect):
```json
{ "info": "Welcome to the BitMEX API...", "version": "...", "timestamp": "..." }
```

**Subscription confirmation**:
```json
{ "success": true, "subscribe": "trade:XBTUSD" }
```

**Error message**:
```json
{ "error": "...", "status": 400 }
```
BitMEX can send `{error}` at any time (e.g. malformed subscribe, rate limit, auth failure).

**Data messages**: always in the form:
```json
{
  "table": "orderBookL2",
  "action": "partial" | "insert" | "update" | "delete",
  "keys": ["id"],
  "types": { "id": "long", "price": "float", ... },
  "filter": { "symbol": "XBTUSD" },
  "data": [ { ... }, ... ]
}
```

`keys` — field names that uniquely identify a row. Used for update/delete matching.
`types` — BitMEX's own type hints (metadata only, doesn't affect the JSON types).
`filter` — reflects what was subscribed to. Present on `partial` for filtered subs.

### Action semantics

- **partial**: full snapshot, replaces all stored data for that table/symbol. Always the first message after subscribing. A partial with empty `data` and a `filter.symbol` still signals "subscription active, no current rows".
- **insert**: append new rows.
- **update**: find existing rows by `keys`, merge new fields into them (partial update — BitMEX only sends changed fields).
- **delete**: find existing rows by `keys`, remove them.

Deltas before a `partial` must be discarded (subscription not yet initialized). The nodejs client enforces this.

### Tables and symbols

Some tables carry no `symbol` field (account-wide data): `account`, `affiliate`, `funds`, `insurance`, `margin`, `transact`, `wallet`, `announcement`, `connected`, `chat`, `publicNotifications`, `privateNotifications`. The nodejs client identifies these via a hardcoded list and routes them differently.

Other tables are always per-symbol: `instrument`, `orderBookL2`, `orderBookL2_25`, `orderBook10`, `quote`, `trade`, `execution`, `order`, `position`, `liquidation`, etc.

`chat` uses `channelID` as its grouping key instead of `symbol` — this is exposed via a `filterKey` field in the message.

### Heartbeat

BitMEX expects a ping at least every 60 seconds or it drops the connection.

The nodejs client sends a text `"ping"` frame every 30s; BitMEX replies with text `"pong"`.
Note: this is application-level ping, not WebSocket protocol-level ping frames.
Broadcast uses WS protocol-level `ws.ping()` instead — this is also valid and arguably better.

### Close codes

- **1000** (Normal close): BitMEX closes cleanly. Usually preceded by a maintenance announcement. The nodejs client treats this as terminal (no reconnect). Broadcast reconnects — fine for a server process.
- **1001** (Going away): server shutting down. Treat same as 1000.
- **1006** (Abnormal closure): not sent by BitMEX — generated by the ws library when the TCP connection drops without a WS close frame (network failure, idle timeout, server crash). Both clients reconnect.
- **1011** (Unexpected condition): BitMEX-side error. The nodejs client treats this as terminal. Broadcast reconnects — acceptable.

### HTTP upgrade errors (during WS handshake)

The `ws` library fires `unexpected-response` if the server returns non-101. The nodejs client handles:
- **401**: terminal — bad credentials, retrying is pointless.
- **502/503**: retriable — maintenance. Enforces minimum 5s before first retry.
- Other: terminal.

Broadcast has no `unexpected-response` listener; the `ws` library falls back to emitting `error`, which broadcast catches and logs, then the `close` event fires and triggers a normal reconnect. A 401 would cause broadcast to retry forever — acceptable since credentials are static config and wrong credentials are an ops issue, not a runtime issue.

### Reconnection

The nodejs client uses exponential backoff: 1s → 2s → 4s → ... → 60s cap, reset to 1s on successful connect.

On reconnect, it re-subscribes to all active channels by listening to its own `open` event. Subscriptions survive reconnection automatically.

## Delta parser (`deltaParser.js`)

Maintains in-memory state as `_data[tableName][symbol]` → array of current rows.

```
partial  → replace store, record keys list
insert   → append to store
update   → find by keys, merge new fields (creates new object, does not mutate)
delete   → find by keys, remove
```

Enforces a `maxTableLen` cap (default 10,000) as a FIFO queue per table/symbol — oldest rows are dropped. This prevents unbounded memory growth for append-only tables like `trade`.

**This is the most reusable piece for building a replay server.** When a client subscribes to a table, the replay server must send a `partial` containing the current state of the book at that point in time. To build that snapshot from stored MongoDB documents (which are individual deltas), you apply them in order using this exact logic. The deltaParser can be used server-side as-is for this purpose, or ported to TypeScript.

## Stream validation

On startup, the client makes an HTTP GET to `/schema/websocketHelp` on the BitMEX REST API. This returns the full list of valid public and private stream names. `addStream` validates against this list and throws on unknown table names.

**Implication for a local WS clone**: if bots use the nodejs client, the local WS server must also implement `GET /api/v1/schema/websocketHelp` returning the same structure, or you fork/patch the client to skip this step.

## Unified client API — how to use for tradebot

The nodejs client accepts a custom `endpoint` option:
```js
new BitMEXClient({ endpoint: 'wss://localhost:9001/realtime' })
```

This means bots can point at the real BitMEX, a local replay server, or an accelerated replay server by changing only config. The client code is identical.

The HTTP stream validation call also uses a configurable `httpEndpoint`. The local server needs to serve that endpoint too, or the fork approach.

## What broadcast already does correctly vs. this client

| Concern | Official client | Broadcast |
|---|---|---|
| Reconnect on close | Exponential backoff, reset on open | Same ✓ |
| Re-subscribe on reconnect | Via `open` event listener | Via `ws.on('open', ...)` ✓ |
| Heartbeat | Text "ping" every 30s | WS protocol ping every 30s ✓ |
| 401 handling | Fatal, no reconnect | Retries forever (acceptable) |
| CLOSE_NORMAL (1000) | Terminal | Reconnects (acceptable for server) |
| Delta accumulation | Yes, per table/symbol | No — intentionally forwards raw messages |
| Stream validation | Yes, via REST | No (not needed for a publisher) |
